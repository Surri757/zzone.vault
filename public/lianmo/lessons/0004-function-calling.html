DAY 02 · 第 2 题（AGENT 方向）· 难度 ⭐+

Function Calling 完整流程——模型自己执行函数吗？工具描述怎么写？失败了怎么办？

附带考点：意图与执行分离 · 工具 schema 设计 · 参数幻觉防护 · 错误回喂自纠
真题源：腾讯/字节/海外 GenAI 岗通用（美团「FC 三连炮」面经；OpenAI 官方文档即标准答案） 佐证：OpenAI Function Calling Guide（2023-06 推出）· Anthropic Tool Use 文档 · 微软 AI Agents 第 4 课 改写声明：JSON 为简化示意，字段随 API 版本略有差异

S1🎭 开场：昨天它够不着 r，今天教它正式伸手

昨天第 1 题的结论是：模型的盲区要交给工具。你问「北京现在多少度？」——裸模型只能抱歉：「我无法获取实时天气」。而配了 Function Calling 的模型会做一件完全不同的事：向你声明过的工具发出一张结构化的"点菜单"，让你写的程序去执行，拿到结果再回答。

一句话：FC 是模型"伸手拿工具"的正式机制——模型点菜，你的厨房做菜。它由 OpenAI 在 2023 年 6 月正式推出，如今是所有 Agent 的地基动作（ReAct 里的 Act、昨天演示器里的"调用工具"，底层都是它）。

S3🔧 工具声明怎么写：description 是写给谁看的？

三个防"参数幻觉"的硬手段（面试 L2 的得分点）：

  • 枚举约束：只接受 "celsius"/"fahrenheit"，模型编出 "warm" 当场被 schema 拦截
  • 必填 + 默认值：city 必填、unit 可默认——减少模型自由发挥的空间
  • 服务端二次校验：程序执行前再验一遍（模型输出的是"意图"，不可无条件信任）

S5🔁 失败了怎么办：错误回喂，让模型自纠

S6🔁 面试官追问链（点开前先自己答）

L1 · 「模型自己执行函数吗？」
💡 提示：如果模型能直接执行代码，谁为误删数据库负责？
想想"点菜的人"和"做菜的厨房"为什么必须是两方。

答案要点：① 从不执行——模型只输出结构化的调用意图（工具名+参数 JSON），真正执行的是调用方程序；② 这是刻意设计的安全边界：权限、鉴权、沙箱都掌握在程序侧；③ ChatGPT 里的"代码解释器"是官方产品预置的执行环境，本质仍是这个分工。

L2 · 「工具描述写差了会怎样？参数幻觉怎么防？」
💡 提示：模型挑工具时能看见什么？
只有 name/description/parameters——除此之外它一无所知。

答案要点：① 模型选工具全靠读 schema，description 本质是给模型看的提示词——写清"何时用/何时不用/参数含义"，它就点得准；写得含糊 → 选错工具、漏调、甚至调用不存在的工具；② 防参数幻觉：枚举约束、必填+默认值、服务端二次校验；③ 出错后把错误信息回喂（限次重试），模型多数能自纠——错误也是 Observation。

L3 · 「Function Calling 是怎么训出来的？模型天生就会吗？」（美团三连炮）
💡 提示：昨天讲过训练三阶段里的 SFT——猜猜 FC 靠什么数据？
如果给你几万条"用户问题 → 正确的工具调用 JSON"样本，你拿它们做什么？

答案要点：① 不是天生——厂商用工具调用轨迹数据做 SFT：样本包括"该调时调对工具、正确填参、不该调时忍住不调、调错后纠错"等各类情形；② 深水区：训练数据要覆盖业务逻辑——"会调"与"按业务逻辑正确地调"是两回事（美团原话方向的考点）；③ 延伸：新工具无需重训也能用（模型按 schema 泛化），但复杂工具组合仍受益于微调。这一问直接衔接 D5「训练三阶段」。

S8🌌 发散思考（没有标准答案，值钱的是你的推理）

🌱 发散 1（换场景）：订机票的 Agent，怎么防模型编造日期和城市？

参考思路：把"可选项"变成 schema 的一部分——城市用枚举（仅航线覆盖的城市）、日期用格式校验 + 必填（ISO 日期）、舱位用枚举+默认值；程序侧执行前二次校验，出错把错误信息回喂让它自纠；高危动作（支付）加人工确认。你会发现这题就是今天 L2 + 昨天 L3（护栏）的组合拳——真题往往就是两天的知识拼在一起。

🌱 发散 2（找反例）：什么任务反而不该给模型配工具？

参考思路：① 模型本就掌握的常识问答/写作/翻译——给工具只会增加误调用和延迟（每次"该不该调"都是一次判断）；② 高频确定性流程——直接写代码调用，不需要模型居中决策；③ 对确定性要求极高且模型无法验证结果的场景。工具是给"模型盲区"补的，不是给所有事情加的——能说出这条边界，说明你真的理解 FC 的定位。

S11🎤 60 秒面试答案（把今天的理解压成一段话）

如果你在面试里被问到这道题，可以这样答：
「Function Calling 是模型使用工具的标准机制，五步闭环：开发者声明工具的 name、description 和参数 schema；模型判断需要时输出结构化的调用请求；由调用方程序真正执行；结果作为 tool 消息回喂；模型再基于真实结果生成回答。最关键的设计是意图与执行分离——模型只决策、从不执行，权限始终在程序侧。工具描述本质是给模型看的提示词，写得差会导致选错工具和参数幻觉，防御靠枚举约束、必填校验和服务端二次验证。执行失败时优先把错误信息回喂让模型自纠，连错才熔断。这个能力本身是通过工具调用轨迹数据 SFT 训出来的。」

📎 补课笔记 · Day 02 追问实录（2026-09-28 · 图文版）

追问 1：「parallel function calling 是什么？」

一个回合里，模型同时发出多个 tool_calls——比如你问"明天北京天气怎么样？人民币汇率多少？我日程有空吗？"，模型一次返回 3 张"点菜单"（查天气、查汇率、查日程），你的程序并行执行三道菜，再把 3 份结果一起回喂。延迟从 3 段串行相加变成约等于最慢的那一段。面试加分点：只有互不依赖的调用才能并行——"先查城市再查该城天气"这种依赖链必须串行，模型判断依赖关系本身就是考点。

追问 2：「ReAct 里的 Act 和 FC 是一回事吗？」

不是一回事，但站在同一个位置。ReAct 是决策框架——规定"何时该行动（Thought 之后）、观察回来怎么进入下一轮"；FC 是 Act 这一步的标准化实现——以什么格式把行动发出来（工具名+参数 JSON）。类比：ReAct 是战术手册，FC 是传球技术。冷知识（面试可秀）：ReAct 原论文（2022）比 FC（2023-06）更早，当时模型输出的是自由文本 Action，靠正则解析——容易碎；FC 出现后，Act 有了结构化的"官方传球姿势"，工程可靠性大幅提升。

💬 卡住了？随时回到对话里直接问我：「parallel function calling 是什么？」「reAct 里的 Act 和 FC 是一回事吗？」——追问本身就是最好的学习。
