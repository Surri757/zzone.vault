DAY 02 · 第 1 题（基座模型方向）· 难度 ⭐+

上下文窗口是什么？128k 到底能装几本书？窗口越大就越好吗？

附带考点：窗口 vs 参数量 · 超窗三策略 · Lost in the Middle · 长上下文 vs RAG
真题源：各厂通用开场题（字节/阿里应用岗常考 128k 换算；阿里原题「200 万 token 了 RAG 还有何意义」） 佐证：Datawhale《hello-agents》第九章 · Liu et al.《Lost in the Middle》(arXiv:2307.03172) 改写声明：换算为估算区间（随词表浮动），考点保真

S1🎭 开场：先盲猜一下

一个 128k 的上下文窗口，能装下几本《三体》第一部（约 30 万字）？

提示：昨天学过，中文 1 个字 ≈ 1~2 个 token（老词表）。128k ≈ 13.1 万个 token。

S2🪟 什么是上下文窗口：一扇共享的玻璃舱

定义（面试必背）：上下文窗口（context window）是模型一次会话中能"看见"的 token 总量上限——注意三件事：

  • 输入 + 输出共用：系统提示词、对话历史、检索来的资料、你的问题、正在生成的回答，全部挤同一扇窗
  • 它是"内存"不是"硬盘"：会话内有效，关掉就没了，不跨对话持久（跨对话的"记忆"是产品层另做的功能，D3 讲）
  • 它 ≠ 参数量：参数量是模型脑容量（训练完就固定），窗口是单次工作台大小——面试爱考这个混淆

S3📏 128k 是多大？各家的窗口长什么样

换算手感（面试要能脱口而出）：128k ≈ 13.1 万个 token ≈

  • 英文：约 9.6 万个单词（1 token ≈ 0.75 词）
  • 中文：老词表（1 字 ≈ 1.5~2 token）约 6.4~8.5 万字；新词表（≈1.1~1.3）约 10 万字——一本 200~300 页的书
  • 《三体》第一部约 30 万字 ≈ 3.5~4.7 个 128k 窗口——一本都塞不下！

S5📉 反直觉真相：窗口越大 ≠ 越好

窗口大小是容量，不是智力。三个代价 + 一个著名现象：

  • 💰 成本：计费按 token——把 100 万 token 全塞进去，每一轮对话都为这 100 万付费
  • 🐢 延迟：先读完全部上下文才能吐第一个字，窗口越长首字越慢
  • 🧠 注意力稀释：要关注的东西越多，每个东西分到的"注意力"越少
🔭 D10 预告条：窗口还有一个隐藏代价——显存。推理时每个 token 都要缓存 K/V 状态：以 Llama3-8B（32 层/8 KV 头/FP16）为例约 128KB/token，128k 窗口 ≈ 16GB 显存，比模型本身还大。怎么算、怎么省（GQA/量化/PagedAttention），D10 专拆。

S6🔁 面试官追问链（点开前先自己答）

L1 · 「上下文窗口是内存还是硬盘？和参数量什么关系？」
💡 提示：关掉对话再打开，它还记得吗？
ChatGPT 新开一个对话，昨天的内容它知道吗？

答案要点：① 窗口是会话内临时工作记忆（内存），关掉即清空，不跨对话持久；② 参数量是训练后固定的"脑容量"，窗口是推理时单次输入+输出的 token 上限——两者无关（7B 模型可以有 128k 窗口，1T 模型也可能只有 8k）；③ 跨对话"记住你"是产品层用向量库做的长期记忆（D3 讲）。

L2 · 「窗口很大了，为什么还会丢中间的信息？」
💡 提示：注意力是"分蛋糕"还是"无限复制"？
100 个 token 每个分 1 份注意力，和 10 万个 token 每个分 1 份，一样吗？

答案要点：① 注意力权重经过 softmax 归一化——窗口越长，单个 token 能分到的注意力越稀（稀释）；② 位置编码对"开头/结尾"的信号天然更显著，中间位置区分度弱；③ 实证即 U 形曲线（Lost in the Middle, 2023）。对策：关键信息放首尾、检索后 rerank 重排、控制塞入的资料量。

L3 · 「要读 300 万字的资料，怎么办？」（阿里原题变体：200 万 token 了，RAG 还有何意义？）
💡 提示：三个维度——装得下吗？用得起吗？知识会变吗？
算一下 300 万字的 token 数和每轮对话的成本；再想想股票价格、新闻这类会变的知识。

答案要点：超窗三策略——① 截断（保留首尾，丢中间有风险）；② 分层摘要压缩（有信息损失）；③ RAG 外置：资料放外面，只把最相关的片段检索进窗口。而"200 万 token 了 RAG 还有何意义"的标准答法：RAG 仍不可替代——知识可随时更新（不用重训/重塞）、成本低（按需检索几 k token vs 每轮扛全量）、可溯源（能给出处）。长上下文胜在全量理解，RAG 胜在成本/更新/溯源——互补不互替（D12 专拆 RAG）。

S8🌌 发散思考（没有标准答案，值钱的是你的推理）

🌱 发散 1（换场景）：客服 Agent 为什么"隔天就忘了你"昨天说的事？怎么补？

参考思路：窗口是会话级内存——新会话一开，旧内容不在窗内，自然"失忆"。产品层的补法是长期记忆：把历史对话摘要/关键事实存进向量库（硬盘），新会话开始时检索相关片段塞回窗口（把"硬盘"的需要的部分搬回"内存"）。这正是 D3「记忆两档」要拆的架构，也是 Day01 第 2 题四模块里"记忆"模块的落地。

🌱 发散 2（找反例）：Gemini 都 2M 窗口了，为什么没有"一统江湖"、让所有 RAG 失业？

参考思路：① 成本——2M token 每轮的输入费用是 128k 的十几倍，高频产品用不起；② 延迟——首字延迟随上下文变长；③ 中间遗忘仍在——窗口大不等于处处记得牢；④ 更新与溯源——知识变了要重塞，而 RAG 换索引即生效、能给出处。"容量解决的是装得下，装得下 ≠ 用得起 ≠ 记得牢"——能说出这三层，面试官会记住你。

如果你在面试里被问到这道题，可以这样答：
「上下文窗口是模型一次会话里能看见的 token 上限，系统提示、历史、检索资料和输出共享这个额度——它是内存不是硬盘，会话结束即清空，和参数量无关。128k 大约是 6 到 10 万汉字、一本 200 到 300 页的书。但窗口大不等于好：成本和延迟随长度上涨，而且存在 Lost in the Middle——中间信息召回呈 U 形下降，关键信息要放首尾、配合 rerank。超长资料的标准做法是 RAG 外置：知识可更新、成本低、可溯源，和长上下文互补而非互替。」

📎 补课笔记 · Day 02 追问实录（2026-09-28 · 图文版）

追问 1：「为什么 softmax 会稀释注意力？」

一句话：注意力权重是一份总额始终为 1 的"预算"，不是音量。softmax 把所有 token 的得分归一化成概率分布——4 个 token 时每个能分 25%，400 个 token 时每个只分 0.25%。token 越多、竞争者越多，单份越薄；中间位置在"开头/结尾"的位置信号上又不占优，于是召回呈 U 形。这就是"稀释"的全部秘密。

追问 2：「rerank 具体怎么做？」

标准做法是两级漏斗：① 召回——向量检索从全库快速捞回 top-50（便宜但粗，双塔模型各自编码、只算相似度）；② 精排（rerank）——用 cross-encoder 把「问题+文档」拼在一起逐对打分（准但贵，50 对就要 50 次推理）；③ 只有精排后的 top-3~5 进入窗口，并且放在开头或结尾（还记得 U 形曲线吗）。为什么不全程用 cross-encoder？全库一万条文档就是一万次推理——漏斗就是"先用便宜的方法缩小战场，再用贵的方法精挑"。
